# 4.1.2. Evaluación y elección del sistema de gestión de base de datos no relacional

## Motivación del enfoque no relacional

El modelo relacional de **RutaAcadémica** (sección 3.3) garantiza la integridad transaccional de la matrícula. Sin embargo, ciertas entidades del sistema presentan características que se benefician del modelo de documentos:

- **Esquema variable:** los documentos de sesiones de tutoría y de auditoría pueden incluir campos distintos según el contexto operativo (motivo de rectificación, compromisos, valores anteriores y nuevos).
- **Lectura por documento completo:** la consulta de un historial de tutoría o de un panel de riesgo recupera toda la información de un estudiante en una sola lectura, sin necesidad de múltiples joins.
- **Escalabilidad horizontal:** durante los picos de matrícula (hasta 500 usuarios concurrentes, RNF-01), las colecciones de solo lectura —como la disponibilidad de vacantes— pueden replicarse con baja latencia en clústeres distribuidos.

Por estas razones el equipo evaluó tres sistemas de gestión de base de datos orientados a documentos: **MongoDB**, **CouchDB** y **Amazon DocumentDB**.

## Criterios de evaluación

| Criterio | Descripción | Peso |
|---|---|---|
| **Modelo de documentos JSON** | Soporte nativo de BSON/JSON con tipos de datos ricos (arrays, subdocumentos). | Alto |
| **Validación de esquema** | Capacidad de definir JSON Schema Validation para garantizar consistencia (sección 3.4.2). | Alto |
| **Consultas y agregaciones** | Potencia del lenguaje de consulta para los requisitos de la sección 4.4.2. | Alto |
| **Replicación y disponibilidad** | Soporte de replica sets para alta disponibilidad (RNF-03). | Medio |
| **Herramientas gráficas** | Disponibilidad de interfaces de administración y modelado (Hackolade, Compass). | Medio |
| **Licenciamiento** | Disponibilidad de Community Edition gratuita adecuada para el contexto. | Medio |
| **Ecosistema y documentación** | Madurez de la comunidad, drivers y documentación en español. | Bajo |

## Decisión

**Se elige MongoDB Community Edition** como sistema de gestión de base de datos no relacional de **RutaAcadémica**.

### Justificación

1. **JSON Schema Validation nativo:** MongoDB soporta el operador `$jsonSchema` directamente en la definición de cada colección, lo que permite aplicar las validaciones de esquema de la sección 3.4.2 sin capas intermedias de validación en la aplicación.
2. **Aggregation Pipeline:** el potente pipeline de agregación de MongoDB permite calcular estadísticas de riesgo académico, rangos de asistencia y resúmenes de sesiones de tutoría en una sola consulta del lado del servidor, lo que reduce la carga en la capa de aplicación.
3. **Patrones de modelo de datos:** MongoDB es la referencia para los patrones *Embedded Document* y *Subset* (sección 3.4.3), y la documentación oficial ofrece guías específicas para cada patrón.
4. **Hackolade:** la extensión oficial de Hackolade para MongoDB permite generar el diagrama de documentos (sección 4.2.2) y el JSON Schema de cada colección directamente desde la interfaz gráfica.
5. **MongoDB Compass:** la interfaz gráfica permite verificar la validación de esquema y ejecutar las consultas de la sección 4.4.2 de forma visual, lo que facilita la revisión durante la sustentación.
6. **Community Edition gratuita:** la licencia SSPL permite usar MongoDB de forma gratuita en entornos no comerciales, lo que se ajusta al contexto académico del proyecto.

### Colecciones implementadas

Las colecciones definidas en la sección 3.4.1 y cuya estructura se detalla en 3.4.2 son:

| Colección | Patrón principal | Descripción |
|---|---|---|
| `sesiones_tutoria` | Embedded Document | Agrupa todas las sesiones y compromisos de una asignación de tutoría en un único documento, con el perfil del estudiante embebido. |
| `seguimiento_riesgo` | Subset | Almacena el snapshot de riesgo académico de cada estudiante-sección con el historial reciente de indicadores, alertas y asistencias. |
